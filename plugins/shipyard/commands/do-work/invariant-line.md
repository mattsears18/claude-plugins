# Invariant-line token reference (steady-state step E)

Consulted-not-executed reference material split out of [`steady-state.md`'s step E](./steady-state.md#e-invariant-line-end-of-every-steady-state-turn) — the phase-file size cap ([#611](https://github.com/mattsears18/shipyard/issues/611)) left `steady-state.md` with essentially no headroom for a new mandatory token's documentation (see [`setup/01d-orphan-orchestrator-worktree-reap.md`](./setup/01d-orphan-orchestrator-worktree-reap.md) for the precedent of this exact kind of sibling-split). Every token this file documents is REQUIRED on the invariant line per the two format templates in `steady-state.md` — this file only carries the per-token *why* (what it means, when it's set, and the divergence smells it surfaces), which you only need when you're unsure what value to compute or why a token exists at all. The literal requirement to include the token, and the "missing token = contract violation" severity, is unchanged by this split — it's restated compactly here per token, same as before.

`tokens_attributed=<true|false>` is the per-turn evidence flag for step A.0's MANDATORY attribution call:

- **`true`** — step A.0's `bump-tokens` call fired and returned successfully this turn. Required outcome on every **reconcile turn** (a turn where step A actually parsed an agent's return).
- **`false`** — step A.0 didn't fire this turn. Valid ONLY on **dispatch-only turns** (turns with no agent completion to reconcile — the initial pool fill at step 7, drain-poll turns where nothing returned, refresh-only turns triggered by the 5-min fallback).

`tokens_attributed=false` on a reconcile turn is a **contract violation** — the same severity as a missing invariant line or a missing `state=` token. If you find yourself emitting it that way, you skipped A.0. Go back, fire the `bump-tokens` call against the dispatch's usage payload, then re-emit the invariant. The one exception is the **logged-skip case**: if A.0 ran but the dispatch result had no `<usage>` block (or the helper call errored), the orchestrator must have already emitted the corresponding `[bump-tokens] …` advisory line earlier in the turn; in that case `tokens_attributed=false` is honest about the gap rather than a silent skip. A missing `tokens_attributed=` token entirely is a contract violation regardless — re-run A.0's compliance check and re-emit.

`last_fresh_fetch=<HH:MM:SS|"never">` is the per-turn evidence flag for whether the backlog has been re-fetched against the live tracker recently. It is set (UTC time-of-day) any time step C's lightweight backlog re-check fires, any time step D's periodic refresh fires, or any time [drain.md's termination-assertion step 4](./drain.md#termination-assertion) fires. Initial value is `"never"` until the first re-check runs in step 7's initial pool fill.

- **Staleness guard on the terminating idle-proof.** When the idle-proof's `idle_reason="all queues empty (terminating after in_flight drains)"` (the path that triggers handoff to drain), the `last_fresh_fetch` timestamp MUST be **within the last 60 seconds** of `now`. Note the semantics ([#662](https://github.com/mattsears18/shipyard/issues/662)): this idle_reason terminates the **dispatch loop** and hands off to the drain — it is NOT a session-complete signal. Session completion is the stronger [full-completion assertion](./drain.md#termination-assertion) the drain evaluates at exit (every session PR merged or confirmed external-blocked); an empty dispatch pool is only the drain-entry gate, so emitting this idle_reason means "stop dispatching, start driving the tail," never "session done." If it's older — or `"never"` — the invariant line is INVALID: the orchestrator is about to declare termination without verifying the live backlog. Don't emit the line; instead, run the [drain.md termination-assertion step 4](./drain.md#termination-assertion) fetch now, stamp `last_fresh_fetch` with the result, append any net-new issues to `raw_backlog`, retry dispatch from step C, and re-emit the invariant line with the fresh timestamp. This is the mechanical guard against the [#195 failure mode](https://github.com/mattsears18/shipyard/issues/195) — "I'm about to terminate but my last fresh fetch was 2 hours ago" is a contract violation, not a valid terminating idle-proof.
- The 60-second window matches step C's `gh-cached.sh --ttl 60` cache band — if the cache is still fresh, the orchestrator's about-to-terminate fetch hits the cache for ~0 token cost; if it's expired, the fetch goes live and the cost is one `gh` call.
- A missing `last_fresh_fetch=` token entirely is a contract violation regardless — re-run a backlog re-fetch and re-emit.

`unfiltered_open_count=<u>` is the per-turn evidence flag for the size of the wide-fetch universe BEFORE the client-side eligibility filter ran. It is set whenever step C's lightweight backlog re-check fires, whenever step D's periodic refresh fires, or whenever [drain.md's termination-assertion step 4](./drain.md#termination-assertion) fires — the same three call-sites that stamp `last_fresh_fetch`. Initial value is `0` until the first re-check runs in step 7's initial pool fill.

- **Divergence smell.** When `raw_backlog` is `0` but `unfiltered_open_count > 0` (in particular, when the gap is large — `raw_backlog=0` against `unfiltered_open_count=29`), that's a load-bearing signal the client-side filter dropped every issue. This is exactly the failure mode [#332](https://github.com/mattsears18/shipyard/issues/332) documented: a regression in the filter pass produces a false-empty backlog and the orchestrator drains while workable issues sit invisible. The user (and the next session's orchestrator) can spot the smell from the invariant line alone without needing to manually re-run `gh issue list`. This is purely an observability token — the orchestrator does NOT auto-retry on divergence; the gap is surfaced as a diagnostic for human (or future automated) investigation.
- A missing `unfiltered_open_count=` token entirely is a contract violation — re-run a backlog re-fetch (which sets both `last_fresh_fetch` AND `unfiltered_open_count` in one pass) and re-emit. The token defaulting to `0` on the initial pool-fill turn is acceptable; the violation is the token's complete absence from a turn that already fetched the backlog.

`me_assigned_open=<N>` (added in [#1194](https://github.com/mattsears18/shipyard/issues/1194)) is the per-turn evidence flag naming the specific bucket a wrong client-side filter is most likely to erase: issues the gh-authenticated user (`@me`) is currently assigned to, counted from the wide-fetch payload BEFORE the client-side filter runs — the same call and the same moment `unfiltered_open_count` is counted, at [step C's lightweight backlog re-check](./steady-state.md#c-dispatch-a-replacement-if-work-remains--mandatory-action) or [drain.md's termination-assertion step 4](./drain.md#termination-assertion). `unfiltered_open_count` alone can diverge from `raw_backlog` for entirely legitimate reasons (untrusted-author issues, dispatch-gate-labeled issues) — it doesn't by itself tell you *which* bucket a regression dropped. `me_assigned_open` is narrower and load-bearing precisely because `@me`-assigned issues PASS the correct filter by design (that's the entire point of [#332](https://github.com/mattsears18/shipyard/issues/332)'s rework — a prior session's self-assign is the resumable-work case): a healthy filter's output always includes every `@me`-assigned open issue somewhere in `in_flight` ∪ `ready_issues` ∪ `raw_backlog` ∪ `deferred_issues` ∪ issues already closed this session.

- **Divergence smell, self-assign class.** When `me_assigned_open > 0` but the count of `@me`-assigned issue numbers actually present across `in_flight` / `ready_issues` / `raw_backlog` / `deferred_issues` / this-session-closed is smaller than `me_assigned_open`, that is a filter regression on the exact assignee gate — a hand-rolled or mis-derived client-side filter dropped a self-assigned, resumable issue. `raw_backlog=0` sitting next to `me_assigned_open>0` is not an empty backlog; it is this failure mode, reproduced. Same posture as `unfiltered_open_count`'s divergence smell: purely observability, no auto-retry — the gap is a diagnostic for human (or future automated) investigation. (**Only when `backlog.respect_assignees: true`** per [#1248](https://github.com/mattsears18/shipyard/issues/1248).)
- A missing `me_assigned_open=` token entirely is a contract violation with the same severity as a missing `unfiltered_open_count=` token — re-run the backlog re-fetch (which stamps both in the same pass) and re-emit. Defaulting to `0` on the initial pool-fill turn is acceptable; the violation is complete absence on a turn that already fetched the backlog.

`operator_q=<N>` / `operator=<active|skipped|unreachable>` are the per-turn evidence tokens for the [operator layer](./operate.md) ([#1193](https://github.com/mattsears18/shipyard/issues/1193)) — the same "is the mandatory layer actually running" gap the `tokens_attributed` and `state=` tokens close for their own layers, applied to the operator queue. Before [#1193](https://github.com/mattsears18/shipyard/issues/1193), the invariant line carried no `operator_queue` signal at all: an orchestrator that never loaded [`operate.md`](./operate.md) — never ran the preflight, never enqueued, never drained — emitted a perfectly well-formed invariant line every turn, indistinguishable from a session where the operator layer ran and legitimately found nothing to do. The [termination assertion's `operator_queue`-must-be-empty gate](./drain.md#termination-assertion) doesn't catch this either — it only checks the queue is empty, not that the layer ever ran, so an unpopulated queue and a drained queue pass it identically.

- `operator_q=<N>` is the current length of `operator_queue` (the same field [`operate/01-queue-and-authorization.md`](./operate/01-queue-and-authorization.md) enqueues into and [`operate/02-execution-and-playbooks.md`](./operate/02-execution-and-playbooks.md) drains). It is read fresh at invariant-line-emission time, not cached.
- `operator=<active|skipped|unreachable>` reports whether the operator layer's preflight actually ran and found something to drive with, set **once** and held for the rest of the session — no per-turn recomputation needed, since the value can't change mid-session:
  - **`skipped`** — the run carries `--no-operate` / `--hands-off`; the operator layer is never loaded and `operator_queue` stays empty by design. This value is known at argument-parse time, before [`operate.md`](./operate.md) would otherwise load.
  - **`unreachable`** — [`operate.md`'s preflight](./operate.md#preflight--detect-gaps-and-guided-setup) ran (the layer is NOT opted out) but found no live-session browser backend reachable — the [degradation path](./operate.md#degradation--no-backend-reachable). The code loop still runs to completion; `operator_queue` items are surfaced as hand-backs instead of driven.
  - **`active`** — the preflight ran and selected a backend (headless, `claude-in-chrome`, or `chrome-devtools-mcp`). The normal case.
  - Set immediately after the preflight resolves (or immediately at arg-parse for `skipped`) — before [setup.md step 7's initial pool fill](./setup/07-pool-fill.md#7-initial-pool-fill), so it holds a determined value on every steady-state turn from the first invariant line onward. Unlike `last_fresh_fetch`, there is no `"never"` placeholder state: the preflight (or the opt-out check that bypasses it) always resolves before the first turn that could emit an invariant line.
- **A missing `operator=` token entirely is the exact contract violation [#1193](https://github.com/mattsears18/shipyard/issues/1193) reports** — the same severity as a missing `state=` or `tokens_attributed=` token. If you find yourself emitting the invariant line without it, you skipped loading [`operate.md`](./operate.md)'s preflight (or skipped recording its outcome) — go back, run the preflight (or confirm the `--no-operate`/`--hands-off` opt-out), and re-emit.
- This is purely an observability pair, like `unfiltered_open_count` — the orchestrator does not auto-retry or auto-load the operator layer off these tokens; they exist so a silently-skipped layer is visible on a single turn's output instead of only at end-of-session, when a human happens to notice `agent-console` issues sat untouched.

`awaiting_ext=<ae>` (added in [#1390](https://github.com/mattsears18/shipyard/issues/1390)) is the current length of the [`awaiting_external`](./session-state-file.md) park queue — workers that returned the terminal `awaiting-external` outcome and are waiting on a long external job (a dispatched CI run, an EAS/store build, a deploy) while the orchestrator owns the poll. It is read fresh at emission time, not cached. `awaiting_ext=0` is the common case. A **non-zero** value is the one signal that distinguishes "this session has idle slots because there is genuinely nothing to do" from "this session has idle slots because near-complete work is parked on a clock" — without it, a parked worker is invisible on every surface the operator actually watches, which is how the [#1390](https://github.com/mattsears18/shipyard/issues/1390) repro's worker ended up killed as if it had hung. Deliberately **excluded** from the [under-dispatch self-check](./steady-state.md#e-invariant-line-end-of-every-steady-state-turn)'s queue sum: a parked entry is not dispatchable work, and counting it there would demand a dispatch the orchestrator must not make. It IS a [termination-registry row](./drain.md#termination-assertion), so a non-zero value blocks the session from declaring itself done. A missing `awaiting_ext=` token is a contract violation with the same severity as a missing `operator_q=` token.

`peers=<p>` (added in [#1204](https://github.com/mattsears18/shipyard/issues/1204)) is the count of other live `/shipyard:do-work` sessions this session's [setup step 1.65](./setup/01-repo-recovery.md#165-detect-live-peer-sessions-on-this-repo-1204) detected working the same repo — `.peer_sessions.count` from the session-state file, set once at setup and held for the rest of the session (no per-turn recomputation, same posture as `operator=`). `peers=0` is the overwhelmingly common case and carries no special handling. `peers>0` means [step 4's peer-claimed drop rule](./setup/04-backlog-divert.md#4-fetch--rank-the-backlog) excluded that peer's `.in_flight[].target` set from `raw_backlog` — evidence, in the same spirit as `operator_q`/`operator=`, that the orchestrator noticed and accounted for something it could otherwise have silently duplicated. A missing `peers=` token is a contract violation with the same severity as a missing `operator=` token — re-run step 1.65 and re-emit.

`disk_free_mb=<N|"unknown">` (added in [#1261](https://github.com/mattsears18/shipyard/issues/1261)) is the free-space reading (megabytes, on the volume holding `.claude/worktrees`) from the [disk-space backpressure check](./disk-space-guard.md) — set every turn step C runs, reusing that same read rather than probing again at emission time. `"unknown"` means the probe itself couldn't read free space this turn (an unreadable path, `df` unavailable) — not evidence of a low-disk condition, since the check fails open on an unreadable result by design.

- **Divergence smell.** A `disk_free_mb` reading that keeps trending down turn over turn, or repeatedly reads below `worktree_reap.disk_free_floor_mb` even immediately after the guard's own `reap-stale` sweep ran, is the mid-session accumulation issue [#1261](https://github.com/mattsears18/shipyard/issues/1261) documents — the per-completion reap points are falling behind faster than the backstop sweep can reclaim, or the sweep's `--max-per-session` cap is too low for this session's dispatch rate. Same posture as every other divergence smell on this page: purely observability, no auto-retry beyond the one sweep the guard already ran — the trend is a diagnostic for a human (raise the floor, raise the cap, lower `concurrency`, or investigate why a specific completion path's reap isn't firing) to act on, not something the orchestrator escalates on its own.
- A missing `disk_free_mb=` token entirely is a contract violation with the same severity as a missing `peers=` token — re-run the [disk-space backpressure check](./disk-space-guard.md) and re-emit.
